# 架构重构方案（架构师视角）

> 本文从架构师视角给出本工程的重构设计：现状评估 → 问题清单 → 目标架构 → 分阶段重构计划。
> 依据为 2026-08 全仓库只读审查（关键论断标注源码位置），与《多步漂移优化方案.md》互补：
> 那份文档回答"练什么损失/配什么参数"，本文回答"代码结构怎么改才能让那些改动安全、可验证地落地"。
> 只做设计落盘，不含代码改动。

## 1. 背景与目标

工程已演进四代模型（v1→v2→v3/v3a→v4），主线从 `scripts/` 迁移到 `new_v4_dict_input/`，部署落在 C++ 潜空间 QP-MPC。演进是"叠加式"的：新管线在旧管线旁生长，旧代码未下线，导致当前同时存在多套同职责实现。多步漂移的优化（P0/P1 清单）需要频繁改动损失、评估与导出——**当前结构下这类改动要同步维护 2~3 处拷贝，且口径校验缺位**，重构是漂移优化的前置条件。

重构目标（按重要性）：

1. **单一事实源**：rollout、损失、模型加载、归一化统计各只有一份实现；
2. **口径可校验**：训练→评估→导出→C++ 的关键口径（dt、pred_len、归一化）机器可查，错配即报错；
3. **改动半径可控**：新增/修改一个损失项或一类模型只动一个文件；
4. **不破坏现有能力**：每阶段完成后全部测试与冒烟通过，ckpt 向后兼容。

## 2. 现状架构总览

分层与数据流（依赖方向基本单向，这是现状最大的优点）：

```
rosbag → scripts/data/ → data/*.npz
  → 训练层   scripts/train_v2.py (1344 行, v2/v3) | new_v4_dict_input/train_v4_dict_input.py (1255 行, v4 主线)
  → 模型库   koopman/model_v1_v2.py (127) / model_v3.py (242) / new_v4_dict_input/model_v4_dict_input.py (209)
  → 评估库   koopman/evalkit.py (1936 行: rollout+指标+绘图+落盘+verdict+CLI)
  → 导出     koopman/export/rollout.py + train_v2.py:302 YAML | new_v4_dict_input/export_v4_onnx.py (631) / export_v4_encode_weights.py (154)
  → C++      cpp/koopman_control/ (9 模块, src 合计 ~1740 行, 划分健康)
```

C++ 侧模块边界清晰（encode / latent_model / decoder / qp / controller / config 各一文件，单文件均 <400 行），**本次重构不动 C++ 结构，只补接口契约**（见 §3 C-4、§5 阶段 3）。

## 3. 架构问题清单

### A 级：结构性问题（决定改动半径）

- **A-1 三套并行 rollout 实现**：训练 `train_v4_dict_input.py:298-324`、评估 `evalkit.py:208-310`、导出 `koopman/export/rollout.py:12-55`。协议一致性靠注释与 `tests/test_rollout_equivalence.py` 人工维持。任何 rollout 语义改动（噪声、反归一化、位姿积分）都要改三处，漏一处即静默分叉。
- **A-2 依赖方向倒置与私有调用**：`evalkit.py:838-845` 惰性反向 import `new_v4_dict_input`（koopman→v4 训练包）；`train_v2.py:169`、`reselect_v3a.py:72` 直接调 `ek._flatten_segments` 私有函数。模型分发靠 `model_class` 字符串 if-else（`evalkit.py:831-866`），新增模型要改评估库内部。
- **A-3 巨型文件**：`evalkit.py` 1936 行（rollout / 指标 / 绘图 / 落盘 / verdict / CLI 六职责）、`train_v2.py` 1344 行（Dataset / EMA / 损失 / 验证 / CLI / 主循环一体）、`train_v4_dict_input.py` 1255 行同构。损失函数与训练循环耦合在单文件，改损失必须在大文件里动手术。

### B 级：一致性/口径问题（直接导致错误结果）

- **B-1 best ckpt 选择口径随 curriculum 漂移**：验证 rollout 用当前 `pred_len`（`train_v4_dict_input.py:1013`），`best_metric` 跨阶段不重置（`:1089-1094`），部署模型可能由短 horizon 口径选出。
- **B-2 配置解析缺陷**：`merge_yaml` 用 `o in argv` 精确匹配检测显式参数（`train_v4_dict_input.py:685-687`），`--epochs=120` 等号形式识别失败 → YAML 静默覆盖 CLI。
- **B-3 口径参数与 ckpt 脱钩**：eval/export 的 `--dt`/`--pred_len` 不从 ckpt args 读取（dt=4s ckpt 漏传即口径错误且无报警）；`export_v4_encode_weights.py:97` 的 `--dt` 仅写 YAML 无校验；`run_v4_dt4s.sh:48` 硬编码 `--dt 4.0`；`ONNX导出说明.md` 口径已过时。
- **B-4 C++ 侧契约缺校验**：latent YAML 无 dt 字段，与 `mpc_config.yaml` 的 dt 靠人肉对齐；ONNX plant 的图内步长与 config dt 错配无运行时检查（`states[1]` 语义静默错误）；`u_prev` 未接入导致首块速率约束锚定零控制（`motion_koopman_mpc.cpp:19-41`）；OSQP 失败直接抛异常（`latent_mpc_qp.cpp:368-372`）。

### C 级：卫生问题（持续产生维护税）

- **C-1 重复实现**：`load_v4_model` 三份（eval/export_onnx/export_encode_weights）、`write_per_step_csv` 两份、`_pick_quantile_indices` 两份、plot 函数族跨文件近似重复；YAML 导出在 `train_v1.py:93-113` 与 `train_v2.py:302-342` 各一份；`composite_v3a` 公式在 `train_v2.py:662-678` 与 `reselect_v3a.py:51-61` 各一份。
- **C-2 死/支线代码**：`train_v1.py`（254 行）已被 v2 完全取代；MMG 支线（`mmg_model.py`/`mmg_residual.py` + 3 个 scripts）精度已验证优于 v4 但未接入导出/MPC；`estimation/kalman.py` 为孤立参考实现。
- **C-3 名不副实**：`ResidualConvBlock` 的 depthwise Conv1d 作用在长度 1 的轴上，实为逐点缩放（`model_v1_v2.py:6-22`）；v4 `encoder_arch="conv"` 默认值为兼容旧 ckpt 保留的退化路径。

## 4. 目标架构设计

### 4.1 分层原则

- `koopman/` 收敛为**纯核心库**：模型、rollout、损失、指标、数据加载，全部无 CLI、无训练循环、无副作用；
- 训练管线（`scripts/train_*.py`、`new_v4_dict_input/`）只做"组装"：解析配置 → 数据 → 模型 → 损失 → 循环；
- 一切跨阶段共享的逻辑（rollout 语义、模型加载、复合选模指标、YAML/ONNX 导出）必须住在 `koopman/`，由管线调用，禁止反向。

### 4.2 关键设计决策

**D-1 单一 rollout 内核**（解决 A-1）。在 `koopman/rollout.py` 提供唯一实现：

```python
def rollout(model, z0, U, *, noise_std=0.0, ctrl_noise_std=0.0,
            denormalize=False, integrate_pose=False, training=False):
```

训练/评估/导出三处改为传不同开关调用同一函数。`tests/test_rollout_equivalence.py` 从"验证三份拷贝一致"改为"验证开关组合行为正确"，测试意图不变、维护面收敛。

**D-2 模型注册表**（解决 A-2）。`koopman/models_registry.py` 提供 `register(name)` 装饰器 + `build_from_ckpt(ckpt)`；各模型文件自注册（v4 模型也注册进来，消除 koopman→v4 的反向 import）。evalkit、eval_v4、export 全部走 `build_from_ckpt`。`_flatten_segments` 提为公开 API `koopman/data.py: flatten_segments`。

**D-3 ckpt 是唯一配置事实源**（解决 B-1/B-3）。eval/export 脚本默认从 ckpt args 读取 `dt/pred_len/model_stride`；显式传参与 ckpt 不一致时**报错而非静默**（提供 `--force` 豁免）。`best_metric` 在 curriculum 到达 `pred_len_max` 时重置（漂移方案 P0-3 的架构落点）。修复 `merge_yaml` 的等号参数检测。

**D-4 部署契约显式化**（解决 B-4）。latent YAML 增加 `dt`、`ckpt_id` 字段；C++ 加载时与 `mpc_config.yaml` 交叉校验，不一致拒绝启动。ONNX plant 同理在启动时校验图内步长语义。OSQP 求解失败降级为"保持上一拍控制"并计数告警。`u_prev` 接入属功能修复（漂移方案 P0-5），不在结构重构范围，但契约校验要拦住它再发生。

**D-5 损失组件库**（解决 A-3 中损失不可组合的部分）。`koopman/losses.py` 把每项损失实现为纯函数 `(model, batch, rollout_out, weights) -> (value, aux)`，训练脚本只做加权求和与 ramp/curriculum 调度。v3a 的 `L_bias`/`L_slope` 以此形式移植回 v4（漂移方案 P0-2 的架构落点），后续新增损失项只动这一个文件。

### 4.3 目标目录结构（收敛后）

```
koopman/
  models/ 或保留 model_*.py   # 各代模型 + registry（v4 模型迁入或注册桥接）
  rollout.py                  # D-1 唯一 rollout 内核
  losses.py                   # D-5 损失组件库
  metrics.py                  # 从 evalkit 拆出：发散/逐步/漂移指标
  data.py                     # flatten_segments 等公开数据 API
  eval/                       # evalkit 拆分：runner / verdict / plotting / io
  export/                     # YAML + ONNX 导出（唯一实现）
new_v4_dict_input/            # v4 训练管线：CLI、dataset、训练循环（瘦身为组装层）
scripts/                      # 历史管线（v2/v3 冻结维护）与数据脚本
cpp/                          # 结构不动，补契约校验与降级
```

注意：**v2/v3 管线不重写**，只做冻结（标记 legacy、停止新功能）；重构火力集中在 v4 主线与 koopman 核心库。

## 5. 分阶段重构计划

每阶段独立可交付、可回滚，完成后跑全量测试（`pytest tests/`）+ 训练/评估冒烟（`--smoketest`）+ ONNX 导出校验。

### 阶段 0：低风险收敛（0.5~1 天，纯去重与 bug 修复，无行为变化）

1. 修复 `merge_yaml` 等号参数检测（B-2）；
2. `load_v4_model`、`write_per_step_csv`、`_pick_quantile_indices` 提为 `new_v4_dict_input/common.py`（或先入 `koopman/`），三处调用改引用（C-1）；
3. `composite_v3a`、YAML 导出各保留一份共享实现（C-1）；
4. `best_metric` 在 curriculum 到顶时重置（B-1，漂移方案 P0-3）。

验证：现有测试全绿 + 同种子短训复现指标不变。

### 阶段 1：核心抽取（2~3 天，结构主手术）

1. D-1 单一 rollout 内核落地，训练/评估/导出三处切换；
2. D-5 损失组件库落地，v4 损失栈迁移，`L_bias`/`L_slope` 以组件形式回归（漂移方案 P0-2 随之解锁）；
3. D-2 模型注册表，evalkit 反向 import 移除；`flatten_segments` 公开化；
4. evalkit 拆分为 `metrics.py` + `eval/` 子模块（先物理拆分、不改逻辑）。

验证：`test_rollout_equivalence`、各导出参考测试（`test_v4_encode_reference`、`test_latent_qp_matrices`）全绿；用现有 best ckpt 重跑评估，逐步指标与重构前一致。

### 阶段 2：口径与配置（1 天）

1. D-3：eval/export 从 ckpt args 自动读 dt/pred_len，冲突即报错；
2. latent YAML 增加 `dt`/`ckpt_id` 字段，导出走统一出口；
3. 同步刷新 `ONNX导出说明.md` 等文档口径。

验证：故意传错 `--dt` 必须报错；dt=4s 与 dt=1s ckpt 各走一遍导出→C++ 冒烟。

### 阶段 3：部署契约与兜底（1~2 天，C++ 侧，可与 1/2 并行）

1. D-4：C++ 启动交叉校验 YAML dt ↔ `mpc_config.yaml` dt ↔ ONNX 步长语义；
2. OSQP 失败降级为保持上一拍控制 + 告警计数（替代抛异常）；
3. （配合漂移方案 P0-5）`u_prev` 接入。

验证：`build_mpc_only.sh` 冒烟；构造 dt 错配 YAML 必须拒绝启动；注入求解失败用例验证降级路径。

### 阶段 4：清理（0.5 天，最后做）

1. `train_v1.py` 归档（移入 `scripts/legacy/` 或删除，git 历史可溯）；
2. 为 `ResidualConvBlock`/`encoder_arch="conv"` 补"仅为旧 ckpt 兼容"的显式标注；
3. MMG 支线去留裁决（若漂移方案 P2-2 推进，则补导出链路而非删除）。

## 6. 兼容性策略

- **ckpt 向后兼容**：所有历史 ckpt 必须可加载——注册表按 ckpt 内 `model_class`/`args` 复原旧结构（含 conv encoder 退化路径），旧结构代码只读冻结、不再演进；
- **导出物向后兼容**：latent YAML 新增字段对旧 C++ 加载器须可选（旧加载器忽略新字段），C++ 契约校验上线前给旧 YAML 一个补写 dt 的小工具；
- **行为冻结点**：阶段 0/1 不改变任何数值行为，阶段 2 起才允许"报错变多"（把静默错误显性化本身就是收益）。

## 7. 验收标准

1. 全仓库同一职责无第二份实现（rollout、模型加载、复合选模、YAML 导出）；
2. `pytest tests/` 全绿；v4 训练/评估/ONNX 导出/C++ 冒烟四条链路各跑通一次；
3. 口径错配（dt、pred_len）在 eval/export/C++ 三处均能启动期报错；
4. 新增一个损失项或新模型的改动文件数 ≤ 2（损失库 + 训练配置 / 模型文件 + 注册）；
5. evalkit.py 拆分后单文件 ≤ 600 行。

## 8. 与《多步漂移优化方案》的关系

| 漂移方案条目 | 依赖的本方案落点 |
|---|---|
| P0-2 恢复 L_bias/L_slope | 阶段 1 损失组件库（D-5） |
| P0-3 best 口径修复 | 阶段 0（B-1）/ D-3 |
| P0-5 u_prev 接入 | 阶段 3 |
| P1-2 损失层修补（L_recon 全程、L_lin detach 等） | 阶段 1 之后在组件库内逐条进行 |
| P1-4 评估补度量 | 阶段 1 拆分出的 `metrics.py` 中新增 |
| P1-5 工程收敛 | 即本方案阶段 0/2/3 |

建议顺序：**阶段 0 立即启动**（与漂移方案 P0 同期），阶段 1 完成后漂移方案 P0-2/P1-2 的落地成本最低；阶段 2/3 在上实船前必须完成。
